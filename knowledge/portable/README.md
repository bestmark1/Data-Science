# Журнал трений

Основной выход этапа 0. Пайплайн на Olist существует для того, чтобы этот журнал
породить, а не наоборот.

## Правило ведения

**Потянуло вынести код в модуль — вместо этого запиши трение.**

Обобщение по ходу первого прохода даёт абстракцию, выведенную ровно из одного
примера. Это воспроизводит ту самую угаданную спецификацию, ради устранения
которой этап и затевается. Желание отрефакторить — сигнал, что нашлось трение,
а не задача на рефакторинг.

**Запись делается в момент возникновения.** Заполнение задним числом даёт
«было неудобно» вместо требования и обесценивает этап.

## Что делает запись полезной

Поле `tool_should_have` — «что вместо этого должен был бы сделать инструмент».
Схема отклоняет запись без него. Оно переводит наблюдение из жалобы в
спецификацию, которую можно реализовать.

## Разделение

- `knowledge/portable/` — обобщённые уроки. Едут между местами работы.
- `knowledge/local/` — конкретика места: имена таблиц, колонок, продуктов,
  сегментов. В git не попадает.

Отнесение выполняет схема: запись с `contains_workplace_specifics: true`
обязана иметь `scope: local`. На этапе 0 данные публичные, и всё попадает в
`portable`, но правило и каталоги существуют с первого дня — нарушается оно
однократно и необратимо.
