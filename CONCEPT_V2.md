Вторая редакция. Заменяет исходный документ на 82 раздела. Решения трёх архитектурных ревью приняты — см. [CONSOLIDATED_REVIEW.md](CONSOLIDATED_REVIEW.md), обоснования не дублируются. История: [CONCEPT_SUMMARY.md](CONCEPT_SUMMARY.md) — редакция 1.

**Цель проекта задана автором:** личный инструментарий дата-сайентиста, который переносится между работодателями и отраслями. Новая работа = новый конфиг, ядро не меняется.

---

## 1. Что это

**Личный переносимый инструментарий дата-сайентиста: репозиторий-шаблон и библиотека, превращающие выгрузку данных в воспроизводимый анализ или модель с проверенной корректностью.**

Не продукт для продажи, не платформа, не сервис. Инструмент одного человека, который едет с ним от места к месту.

### Как используется

```
новая работа / новый проект
  → клонировать шаблон
  → заполнить config: источник, маппинг схемы, определения метрик,
                      таргет, момент решения
  → пройти чек-листы вопросов (что спросить у бизнеса и у владельцев данных)
  → audit: отчёт о дефектах данных
  → analysis: baseline → модель → оценка → порог → отчёт
  → пополнить личный журнал: что поймали, что помогло
```

Смена отрасли меняет `config/` и `knowledge/`. `audit/` и `analysis/` не трогаются. Это и есть проверяемая формулировка H1.

### Три уровня, которые нельзя путать

| Уровень | Что это | Как часто создаётся |
|---|---|---|
| **1. Ядро** | инструмент: библиотека, контракты, аудит, анализ, отчёты. Стек фиксируется здесь | **один раз** |
| **2. Проект-экземпляр** | папка + `config.yaml`: где данные, что сущность, что время, что таргет, когда момент решения, какие метрики | на каждую задачу, минуты |
| **3. Этап 0** | разовое упражнение на публичном датасете, чтобы наблюсти спецификацию вместо угадывания | однократно; потом становится референсным примером и eval-фикстурой |

```
projects/
  olist-delivery-delay/  config.yaml   ← учебный
  work1-churn/           config.yaml   ← первая работа
  work1-fraud/           config.yaml   ← там же, другая задача
  work2-demand/          config.yaml   ← другая отрасль
```

Ядро во всех случаях одно. Правка `audit/` или `analysis/` при создании очередного экземпляра — сигнал протёкшей абстракции и критерий H1 (§15).

Стек от датасета не зависит: датасет подставляется на уровне 2.

### Независимость от стека работодателя

Инструмент не встраивается в платформу компании. Он работает с выгрузкой (§3): что бы там ни стояло — Spark, Databricks, Greenplum, Oracle — наружу выходит таблица, и дальше работает локальный Python.

Работа с файлами вместо подключения — не упрощение, а условие переносимости.

### Проверочный критерий концепции

> Если убрать LLM целиком, инструмент должен остаться полезным.

Это не философия: на большинстве серьёзных работ внешняя LLM будет недоступна (§4). Инструмент, теряющий смысл без неё, окажется бесполезен именно там, где нужен.

## 2. Что входит

Полный DS-пайплайн для batch-задач над табличными и event-данными с явной временной осью:

```
профилирование и EDA
готовность данных: PIT, лики, grain, целостность сплита
стратегия сплита
baseline
подготовка признаков
обучение модели
offline-оценка, калибровка
анализ ошибок по сегментам
выбор порога / политики под цену ошибки
воспроизводимый отчёт
```

Плюс ветка диагностической аналитики (почему изменилась метрика) без моделирования.

### Пропорции

Сам фит модели — коммодити. Тонкая обёртка над sklearn / LightGBM / CatBoost, фиксирующая версии, сиды и артефакты. Свой ML-фреймворк не пишется.

Ценность в том, что вокруг модели: корректный сплит, отсутствие лика, честная out-of-time оценка, калибровка, разбор ошибок по сегментам, **выбор порога под цену ошибки вместо максимизации F1**.

### Вне области

| Область | Статус |
|---|---|
| Streaming, survival, графы, мультимодальность | отдельные execution profiles, вне области |
| Регулируемые домены как заявленная поддержка | вне области; инструмент личный, ответственность на пользователе |
| Мультиарендность, хостинг, продажа | вне области |
| Собственные feature store, платформа экспериментов, разметка | не строим |
| Learning Engine, обучаемый router, multi-agent | вне обозримого плана |
| Исполнение действий в проде | вне области |

## 3. Ограничение среды: работа с выгрузкой, а не с подключением

Прийти на работу и направить личный софт на хранилище работодателя нельзя без security review и согласования. Чаще всего согласования не будет.

**Основной режим:** вы получаете выгрузку (CSV / Parquet) или выполняете SQL в согласованной корпоративной среде, результат кладёте локально, инструмент работает с локальными файлами.

**Дополнительный режим:** прямые коннекторы к БД — там, где разрешат. Приятное дополнение, не основа.

Следствия:
- ядро не предполагает живого доступа к warehouse;
- всё, что требует продольного наблюдения источника, — опционально и деградирует до «неизвестно»;
- версионирование датасетов — локальное, по содержимому.

## 4. Ограничение среды: периметр данных и LLM

Внешняя LLM видит то, что ей отправлено. Схема таблиц и имена колонок конфиденциальны сами по себе; значения — тем более.

**Шифрование эту задачу не решает.** Чтобы модель что-то поняла, данные должны быть расшифрованы в момент инференса. Гомоморфное шифрование для инференса LLM практически непригодно. TLS защищает канал, но не от самого провайдера.

Работает другое: **не отправлять того, что нельзя отправлять.**

### Уровни доступа LLM-вызова

Каждый вызов объявляет уровень. Политика проекта разрешает или запрещает.

| Уровень | Что уходит наружу | Где допустимо |
|---|---|---|
| **0** | только текст задачи, ничего из данных | любой провайдер |
| **1** | псевдонимизированная структура: `col_7 (string, card 12043, null 3%)` | одобренный эндпоинт |
| **2** | реальные имена таблиц и колонок, схема | одобренный эндпоинт |
| **3** | значения, примеры строк | **опционально, по умолчанию отключён** |

Ядро работает на уровне 0 — то есть без LLM. Это условие применимости в банке, телекоме и любом месте с настоящим data governance.

### Агрегаты не выводят данные из-под NDA

Распространённое заблуждение: «мы отправляем только метрики, значит всё в порядке». Разделять надо два режима защиты:

- **Персональные данные** — агрегаты из-под них выходят.
- **Коммерческая тайна** — агрегаты являются её ядром. Выручка, конверсия, отток, доля дефолтов, маржинальность по сегментам защищаются в первую очередь. Сводка часто чувствительнее строки: строка — один клиент, сводка — состояние бизнеса.

**Определяющий фактор — не «что отправляем», а «чей эндпоинт».**

| Эндпоинт | Статус |
|---|---|
| Одобренный сервис работодателя (их тенант, их договор, zero-retention) | данные не покидают контур компании; отправка бизнес-чисел обычно разрешена — ради этого контур и разворачивали |
| Личный аккаунт любого провайдера | передача сведений третьему лицу; нарушение NDA независимо от степени агрегации |

Уровень агрегации влияет на риск утечки, но не на факт нарушения.

### Градиент чувствительности

| Что | Чувствительность |
|---|---|
| Метрики качества модели: AUC, калибровка, форма матрицы ошибок, разрыв CV/OOT | низкая |
| Относительные изменения: «упало на 12%», «сегмент A вдвое хуже B» | средняя |
| Названия сегментов, продуктов, клиентов | высокая — раскрывают структуру бизнеса |
| Абсолютные бизнес-величины: выручка, число клиентов, объём портфеля | высшая |

### Режим нормализации чисел

По умолчанию наружу уходят формы и относительные величины, не абсолюты:

```
вместо:  выручка упала с 4.2 млрд до 3.7 млрд в сегменте "Премиум МСК"
уходит:  метрика M1 упала на 11.9% в сегменте S3 (доля 14% выборки)
```

Качество разбора не страдает: чтобы объяснить, где ломается модель и что проверить дальше, абсолютные значения не нужны. Обратная подстановка настоящих названий выполняется локально при сборке отчёта.

Это делает LLM-слой применимым и там, где одобренного эндпоинта нет.

### Вопросы первой недели

Ответ определяется политикой компании, а не техникой. В чек-лист входит: есть ли одобренный LLM-сервис; можно ли отправлять туда агрегированные результаты анализа. **Ответ получить письменно.**

### Уровень 3 по умолчанию пуст

Единственная реальная задача LLM над значениями — определить семантику колонки по примерам («похоже на ИНН», «дата строкой», «ФИО»). **Детерминированные детекторы делают это лучше** маленькой локальной модели: регулярные выражения, парсинг дат, контрольные суммы, энтропия строк, доля уникальных, длина, алфавит.

Поэтому семантический классификатор колонок — детерминированный, а уровень 3 остаётся крючком на будущее (появится локальная модель или инференс-инфраструктура работодателя). **Пайплайн обязан полноценно работать при пустом уровне 3.**

Следствие: значения не покидают машину никогда, и мощность машины перестаёт быть ограничением.

### Конфигурация на рабочем месте

Задаётся один раз при развёртывании инструмента на новом месте, не на каждый проект:

```
llm:
  enabled:   true | false      ← на многих работах будет false
  base_url:                    ← одобренный эндпоинт работодателя
  api_key:
  model:
  max_tier:  0 | 1 | 2         ← что политика разрешает отправлять
```

`enabled: false` — полноценный режим: работает всё, кроме черновиков и объяснений.

### Провайдер-агностичность

Крупные компании обычно запрещают не LLM, а личный аккаунт: у них есть свой одобренный сервис. Каким он будет — Azure OpenAI, Bedrock, Vertex, китайская модель или локальный vLLM — заранее неизвестно. Поэтому провайдер конфигурируется, а не выбирается на этапе разработки.

**OpenAI-совместимый HTTP — фактический общий знаменатель.** Его поддерживают Azure OpenAI, vLLM, Ollama, DeepSeek, Qwen/DashScope, Mistral, Together и большинство остальных. Конфиг из трёх полей покрывает их все:

```
base_url
api_key
model
```

Правила реализации:

- **Тонкий собственный клиент, не фреймворк.** LangChain и аналоги привязывают сильнее, чем сам провайдер. Для Anthropic и Google — тонкие адаптеры за тем же внутренним интерфейсом.
- **Матрица возможностей.** Провайдеры различаются не адресом, а поддержкой structured output, JSON mode, вызова инструментов и длиной контекста. Каждое место вызова объявляет требуемую возможность; для провайдера без неё есть путь деградации (строгий промпт + парсер + валидация схемы — валидация нужна в любом случае).
- **Промпты без вендорских трюков.**
- **Качество модели не влияет на корректность.** Любой выход LLM проходит детерминированную проверку. Слабая одобренная модель повышает долю ручных правок, но не пропускает неверный расчёт.

### Проверка одобренного эндпоинта работодателя

Наличие eval-набора даёт практическую возможность: прогнать его против одобренного на новом месте эндпоинта и получить фактический ответ — годится ли эта модель для LLM-слоя и на каких задачах она сыпется. Без этого вопрос «дело в модели или в промптах» решается месяцами.

## 5. Принципы

Десять проверяемых ограничений.

1. **Валидируется контракт, а не результат.** Ни один инструмент не вызывается вне утверждённого Analytical Contract.
2. **Вычисления детерминированы.** LLM не считает метрики, значимость и размеры выборки.
3. **Каждый claim связан с evidence.** Вывод без ссылки на породившее его вычисление не выпускается.
4. **Эпистемический статус обязателен:** descriptive / predictive / causal + неопределённость.
5. **Всё семейство сравнений хранится.** Отрицательные результаты не выбрасываются, множественность учитывается.
6. **Артефакты неизменяемы**, адресуются по содержимому; `latest` — алиас.
7. **Расширения — данные, не код.** Domain Packs и eval packs не исполняются.
8. **«Ответить нельзя» — допустимый и ожидаемый ответ**, оценивается наравне с содержательными.
9. **Риск крепится к выводу и действию, не к проекту.**
10. **Каждый LLM-вызов объявляет уровень доступа к данным.** Вызов без объявленного уровня запрещён.

## 6. Analytical Contract — центральный объект

Типизированное представление между вопросом и вычислением. Центральный API.

```
вопрос / задача
  → Analytical Contract      ← валидируется здесь
  → исполнимый план
  → результаты инструментов
  → claims, связанные с evidence
```

Без контракта смысловые ошибки неотличимы от корректных решений: запрос, посчитавший метрику по неверной когорте, синтаксически безупречен.

```
population          популяция и eligibility
grain               единица наблюдения
entity_keys         + правила identity resolution
metric_version      ссылка на версионированное определение
as_of               + timezone, календарь, границы полного периода
baseline            с чем сравниваем
exposure            intervention, если есть
outcome             + горизонт наблюдения
estimand            что именно оценивается
assumptions         явный список
computation_plan    план вычислений
claim_evidence      граф связей вывод ← доказательство
epistemic_status    descriptive / predictive / causal + uncertainty
```

## 7. Сопутствующие контракты

Один рабочий процесс, четыре типизированных артефакта с разными основаниями для изменения.

| Артефакт | Содержит | Меняется когда |
|---|---|---|
| **Problem Statement** | задача, objective, тип работы | сменилась цель |
| **Metric Contract** | формула, числитель, знаменатель, фильтры, grain, источники, ограничения, версия, `valid_from/valid_to` | сменилось определение |
| **Decision Contract** | момент решения, доступная тогда информация, горизонт результата, возможное действие, обратимость | сменился процесс |
| **Observation Contract** | почему объект попал в данные, когда результат наблюдаем, какое действие уже влияло, для какой части популяции outcome доступен | новые факты о данных |

**Decision Contract важнее Domain Pack:** явное описание момента решения отсекает модели, статистически хорошие и операционно бесполезные.

**Observation Contract** покрывает класс проблем шире лика: selection и survivorship bias, censoring, delayed outcomes, MNAR-пропуски, policy-induced labels, rejection inference, interference. PIT-корректный датасет может быть непригоден для задачи.

## 8. Время и данные

```
event_time            когда событие произошло
source_available_at   когда стало доступно; допустимо unknown
ingested_at           когда попало к нам
validity_interval     valid_from / valid_to
snapshot_id           версия состояния источника
```

Полная битемпоральность не требуется. `unknown` — легитимное состояние, честно ограничивающее выводы.

### Иерархия доказательств point-in-time

| Уровень | Основание | Сила |
|---|---|---|
| 1 | Immutable event log, transaction-time / bitemporal history + versioned transformation | сильное |
| 2 | Snapshots, time travel, CDC с retention, ingestion logs | среднее |
| 3 | Утверждение владельца + эвристики по схеме | слабое |
| 4 | Продольный хэш-диф партиций | мониторинг мутабельности, **не** доказательство |

При работе с выгрузкой (§3) чаще всего доступны уровни 3 и 2. Это фиксируется и ограничивает выводы, а не игнорируется.

### Состояния доступности

`available / missing / partial / proxy / historically_unavailable` — четыре разные ситуации с разными последствиями, не сводить к бинарному вердикту.

## 9. Детерминированное ядро и LLM-слой

### Детерминированно

Исполнение SQL и Python; расчёт метрик по версионированным определениям; профилирование; проверки качества; grain- и cardinality-контракты; reconciliation tests; временная целостность; формализуемые правила лика; генерация сплитов; power / sample size / MDE; статистические тесты; коррекция на множественность; сезонность (STL/ACF); структурные сдвиги (PELT/CUSUM); learning curves; baseline; обучение модели; offline-оценка; калибровка; анализ ошибок; выбор порога; grounding-проверка; версионирование; регрессионные evals; аудит-лог.

### LLM — опциональный слой

| Поверхность | Уровень доступа |
|---|---|
| Формулировка задачи, черновик Problem Statement | 0 |
| Помощь в заполнении Analytical Contract | 0–1 |
| Разметка подозрительных колонок по структуре и статистикам | 1 |
| Семантический маппинг схемы на контракты | 2 |
| Генерация SQL / кода признаков | 2 |
| Интерпретация результатов и ограничений | 1–2 |
| Adversarial критика вывода | 1–2 |
| Работа с примерами строк | 3 — отключён; заменён детерминированным классификатором колонок |

### LLM не применяется

Выбор KPI и утверждение таргета; вердикт готовности данных; финальное решение о лике; расчёт значимости; causal claim без соответствующего дизайна; изменение определений метрик; классификация риска; роль единственного защитного слоя.

### Чек-листы вопросов работают без LLM

Наборы вопросов по этапам («что спросить у владельца данных», «что уточнить про таргет», «что выяснить про момент решения») — обычные версионированные файлы. LLM делает их диалоговыми, но список полезен сам по себе и на новой работе в незнакомой отрасли является одной из самых ценных частей инструмента.

---

## 10. Data Readiness

Отчёт о **конкретных дефектах**, а не сводный балл. Три состояния на проверку: `verified / contradicted / unknown`.

Содержание: временная доказательность (уровень PIT), grain и корректность join'ов, fanout и двойной подсчёт, применение SCD, согласованность identity, observability меток, целостность сплита, покрытие сезонности, структурные сдвиги, достаточность выборки через learning curves, список вопросов, не решаемых автоматически.

### Гейт не блокирует

Результат — запись о рисках: что выявлено, серьёзность, что принято на веру. EDA и baseline выполняются **до** гейта: дешёвый baseline на грязных данных отвечает на половину чек-листа за час.

Три настоящих блокера: доказанный временной лик; контаминация release-challenge набора; PIT-ненадёжность при необратимом действии.

### Про лик

Формализуемые правила детерминированы. Ablation и эвристика «слишком хорошо» — **triage**: не повышают уровень доказанности без временного или семантического evidence. Легитимный признак может нести большую часть сигнала; лик может быть размазан по коррелированным признакам.

## 11. Моделирование и оценка

Тонкий слой над существующими библиотеками. Фиксируются: версии, сиды, конфигурация, артефакты, окружение — так, чтобы прогон воспроизводился.

```
baseline first          наивный предиктор, историческое среднее,
                        логрегрессия, текущий бизнес-процесс
модель                  sklearn / LightGBM / CatBoost
оценка                  offline-метрики + обязательная OOT-оценка
калибровка              надёжность вероятностей, а не только ранжирование
анализ ошибок           по сегментам, а не общий счёт
порог / политика        под цену ошибки и ожидаемый эффект,
                        не максимизация F1
```

Сложная модель обязана доказать улучшение относительно baseline. Разрыв между кросс-валидацией и out-of-time трактуется как сигнал временного лика, а не как шум.

**Ожидаемая ценность** считается детерминированно и остаётся offline-оценкой: она не является доказательством причинного эффекта.

## 12. Claims, evidence, множественность

Grounding чисел необходим, но недостаточен: он ловит выдуманные числа и пропускает расчёт по другой когорте, перепутанные числитель и знаменатель, неполные периоды, абсолютное изменение, названное относительным, и evidence, не поддерживающее вывод логически.

Для каждого claim: популяция, вычисление, направление эффекта, неопределённость, ограничения, тип допустимого утверждения.

### Множественность

Итеративный скан сегментов, окон и метрик — автоматизированный garden of forking paths. Хранится и различается:

```
exploratory findings
pre-specified confirmatory tests
семейство ВСЕХ выполненных сравнений
результаты после multiplicity correction / FDR
подтверждение на отложенном периоде
отрицательные результаты
```

### Три набора с первого дня

```
development       открытый, используется при настройке
regression        пополняется из провалов, подтверждается вручную

```

**Инвариант GS-1.** Ни один порождённый обучением артефакт не попадает в release-challenge без подписанной записи provenance.

### Пирамида тестовых данных

```
1. инжектированные дефекты      PIT, лики, сдвиги, negative controls
2. messy case bundles           вручную, реальная грязь
3. публичные датасеты с задокументированными ликами
4. реальные рабочие задачи      когда появятся
```

Причинный анализ **не** оценивается по правилу «назвал инжектированную причину»: при недостаточной идентифицируемости правильный ответ — «по этим данным причину установить нельзя».

## 14. Знание и личный журнал

Одно хранилище, типизированные режимы доверия: `retrieved_fact / human_approved / experimental_result / agent_hypothesis`.

Запись: `statement, source, scope, confidence, created_at, validated_by, status, version`. Статусы: `candidate / validated / rejected / deprecated`.

### Личный журнал — недооценённая часть

`knowledge/` накапливается через все места работы: какая проверка какой дефект поймала, какой вопрос надо задать на первой неделе, где обычно врёт витрина, какая гипотеза уже проверялась и была отвергнута.

Через два года это стоит дороже кода и переносится вместе с ним. Часть записей будет содержать сведения работодателя — журнал разделяется на переносимую (обобщённые уроки) и непереносимую (конкретика места) части.

### Impact Chain

`model metric → operational metric → action → outcome → business KPI`, каждая связь: `hypothesized / observationally_supported / experimentally_validated / rejected`.

Статус `rejected` — самостоятельная ценность: не предлагать повторно опровергнутое, снижать survivorship bias.

### Обучение — одна ручная операция

```
failure → diagnosis → regression candidate → подтверждение
       → новая версия eval suite → release report
```

Никакого Learning Engine. Журнал решений по структурным сдвигам (`include / exclude / downweight / separate_regime / indicator`) сохраняется.

## 15. Переносимость между отраслями

### Domain Packs

**Versioned data. Не исполняется. Не влияет на поведение автоматически.**

```
(1) eval-кейсы домена
(2) 10–30 дизамбигуирующих вопросов
(3) priors как варианты с trade-off, никогда как утверждения
```

Типовые objectives и playbooks не хранятся: базовая модель их знает, а хранимая копия расходится с реальностью за полгода.

### Semantic layer

Потребляется через адаптер, если у работодателя он есть (dbt / Cube / LookML), иначе — простой локальный YAML. Система предлагает только дельты, слой с нуля не строит.

### Критерий H1

Не «сколько отраслей поддержано», а: **что пришлось изменить при переходе на новую работу.**

```
config/ и knowledge/ меняются      → ожидаемо
audit/ и analysis/ не меняются     → абстракция держит
if industry == ... в ядре          → провал
```

Правка ядра при втором проекте на ранней стадии провалом не является — второй проект для того и нужен.

## 17. Дорожная карта

Восемь этапов, у каждого работающий артефакт и критерий остановки. LLM появляется на пятом.

| Этап | Артефакт | Критерий остановки |
|---|---|---|
| **0. Пройти путь руками** | публичный датасет, полный цикл до модели, записанный список того, что было муторно | список пуст или всё решается тремя готовыми библиотеками |
| **1. Eval substrate** | 12–20 case bundles: инжектированные дефекты, negative controls, messy cases | рубрика не отличает найденный дефект от ложной тревоги |
| **2. Audit** | отчёт о дефектах `verified / contradicted / unknown` | находит общие вопросы вместо конкретных дефектов |
| **3. Analysis** | сплит, baseline, модель, OOT-оценка, калибровка, анализ ошибок, порог, воспроизводимый отчёт | повторный прогон не воспроизводится или не быстрее ноутбука |
| **4. Config и чек-листы** | шаблон проекта: маппинг схемы, определения метрик, наборы вопросов | заполнение конфига дольше, чем сделать руками |
| **5. LLM-слой** | опциональный, типизированный по уровням, провайдер-агностичный + прогон eval-набора против конкретного эндпоинта | не снижает число смысловых ошибок или неприменим по политике |
| **6. Второй проект в другой отрасли** | conformance report: что переиспользовано, что расширено | `if industry == ...` в ядре |
| **7. Журнал и регрессия** | `knowledge/` + одна ручная learning-операция | журнал не пополняется в реальной работе |

Этап 0 обязателен и заменяет отсутствующий рабочий сценарий: пока вы не прошли путь руками, спецификация будет угаданной.

## 19. Зафиксированный стек

```
Python 3.11+
uv                      зависимости и окружение, lock-файл
Polars                  датафреймы
DuckDB                  SQL поверх файлов, данные больше памяти
LightGBM + CatBoost     модели
scikit-learn            метрики, калибровка, сплиты
pydantic                схемы контрактов: YAML → типизированные объекты
YAML                    формат контрактов
Parquet                 артефакты, адресация по хэшу содержимого
MLflow (file://)        трекинг экспериментов, локально
structlog               прикладные логи
pytest                  прогон eval-наборов
matplotlib              графики; отчёт Markdown → HTML
```

Работа на обычном ноутбуке без GPU **не понижает качество** на объявленном семействе задач:

- **ML на табличных данных** — градиентный бустинг здесь state of the art и обыгрывает нейросети. Лучший выбор по существу, а не уступка железу.
- **Движок обработки** — DuckDB/Polars быстрее pandas и работают с данными, не помещающимися в память. Расширение возможностей, а не ограничение.
- **LLM** — исполняется на стороне провайдера, локальное железо на её качество не влияет.

GPU потребовался бы для зрения, NLP и дообучения больших моделей — это вне семейства задач (§2), и там инфраструктуру предоставляет работодатель.

### Три вида логирования

| Вид | Зачем | Чем |
|---|---|---|
| **Трекинг экспериментов** | сравнение прогонов: параметры, метрики, артефакты | MLflow, бэкенд `file://` |
| **Аудит-трейс** | воспроизводимость и lineage: контракт, данные, версии, claim ← evidence | собственный, решение 4 |
| **Прикладные логи** | что делал инструмент, где упал | structlog в файл |

**MLflow — хранилище прогонов, не источник истины.** Источник истины — неизменяемые артефакты с адресацией по содержимому и граф lineage (решение 4). MLflow получает зеркало для просмотра и сравнения. Обратный порядок привязал бы проект к run-центричной модели данных и разрушил гарантии воспроизводимости.

Бэкенд конфигурируется по тому же принципу, что LLM-провайдер:

```
tracking:
  backend: file              # по умолчанию, ничего не покидает машину
  uri: ./mlruns
  # backend: mlflow
  # uri: http://mlflow.corp.local:5000
```

Облачные трекеры (Comet, W&B, Neptune) в личных аккаунтах **не используются**: логирование метрик модели, обученной на данных работодателя, в сторонний сервис — то же нарушение периметра, что и отправка их в чужую LLM (§4). Правило нормализации распространяется и на трекер: примеры строк не логируются никогда.

### Интерфейс

Отчёт производит скрипт, а не Jupyter. Ноутбук не воспроизводится и не проходит критерий «повторный прогон даёт тот же результат»; остаётся инструментом разведки, но артефакт производит код.
