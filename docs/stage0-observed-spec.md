# Наблюдённая спецификация: выход этапа 0

Требования к `audit/` и `analysis/`, выведенные из прохода по Olist, а не из
предположений. Каждое опирается на конкретное трение из
[журнала](../knowledge/portable/friction-log.md): 39 записей, 22.9 часа ручной
работы.

Правило отбора: требование включается, если трение возникло **и** его устранение
изменило бы результат или сэкономило заметное время. Наблюдения, встретившиеся
однократно и специфичные для Olist, вынесены в §7 и требованиями не считаются.

## 1. Распределение трения

| этап работы | записей | минут | доля времени |
|---|---|---|---|
| Понимание данных (01–03) | 9 | 222 | 16% |
| Таргет и лик (04–05) | 11 | 390 | 28% |
| Моделирование и оценка (06–10) | 13 | 490 | 36% |
| Исправление протокола (11–12) | 6 | 270 | 20% |

**Пятая часть времени ушла на исправление протокола оценки** — и именно она
трижды переворачивала вывод. Это самая дорогая ошибка этапа, и она не в данных
и не в модели.

## 2. `audit/` — проверки данных до моделирования

Все детерминированы. Ни одна не требует LLM.

| # | Требование | Статус |
|---|---|---|
| A1 | Детектировать строковые колонки с датами по образцу значений и помечать как кандидаты во временную ось | предупреждение |
| A2 | Помечать колонки с кардинальностью, равной числу строк, как суррогатные ключи: они не являются идентификатором сущности, даже если названы `*_id` | предупреждение |
| A3 | Считать полные дубликаты строк по умолчанию | отчёт |
| A4 | Проверять монотонность временных меток по объявленному порядку процесса, показывая долю нарушений по каждой паре | требует объявления (§5) |
| A5 | Проверять согласованность категориального статуса и связанных временных меток | требует объявления (§5) |
| A6 | Проверять полноту крайних периодов по объёму относительно медианы и предупреждать об обрыве сбора | предупреждение |
| A7 | Детектировать пропущенные периоды во временном ряду объёма до выбора периода обучения | предупреждение |
| A8 | **Отказываться выполнять join один-ко-многим, когда дальше идёт суммирование**, показывая ожидаемое раздувание до выполнения | **блокирующее** |
| A9 | При join сообщать потери строк с каждой стороны и требовать явного решения вместо вывода из типа join | требует решения |
| A10 | При сравнении двух временных колонок проверять их фактическую грануляцию: колонка с одним уникальным временем суток — это дата, а не момент | **блокирующее** |
| A11 | Проверять связь пропусков с категориальным статусом и помечать пропуск как post-treatment, если он объясняется исходом | предупреждение |
| A12 | Показывать долю строк оценочного окна, выпавших по незрелости метки | отчёт |

Обоснование блокирующего статуса A8: наивный join завысил выручку на 5%.
Двукратная ошибка заметна, пятипроцентная отгружается в прод.

Обоснование блокирующего статуса A10: сравнение момента времени с датой пометило
опоздавшими 1 292 заказа, приехавших в обещанный день — 16.5% положительного
класса.

## 3. `contracts/` — что человек обязан объявить

Ни одно из этого не выводится из данных. Инструмент требует ответа и
отказывается работать без него.

| # | Требование |
|---|---|
| C1 | Доступность признака в момент решения — обязательное поле. Без объявления признак не попадает в обучающую выборку |
| C2 | Третье состояние доступности — «неизвестно» — наравне с «да» и «нет». Такие признаки идут в список вопросов к владельцу данных, а не получают умолчание |
| C3 | Estimand формулируется до вычисления таргета. Инструмент показывает, как меняются популяция и доля положительных при каждом варианте |
| C4 | При таргете, вычисляемом из даты, требуется явный ответ, что означает отсутствие даты |
| C5 | Причины отсутствия события разбираются по категориальному статусу; склейка разных причин в один класс запрещена |

Плюс два требования, детерминированных **при наличии** контракта:

| # | Требование |
|---|---|
| C6 | Отслеживать, какие колонки участвовали в вычислении метки, и помечать их как производные от таргета автоматически |
| C7 | Выводить момент узнавания исхода из определения таргета, а не приравнивать к моменту наступления события |

C6 — самое неочевидное требование этапа. Разметив недоставленные заказы как
опоздавшие, я сделал `order_status` их точным индикатором. Связь возникла не в
данных, а в определении, и проверка данных её объяснить не могла.

C7 изменило зазор сплита: p95 задержки 29 → 26 дней, максимум 209 → 145.

## 4. `analysis/` — моделирование и оценка

| # | Требование | Статус |
|---|---|---|
| N1 | Выводить распределение задержки метки и предлагать минимальный зазор для временного сплита | автоматически |
| N2 | Строить временной сплит по моменту узнавания исхода, показывая, сколько строк выпадает между выборками | автоматически |
| N3 | Проверять стационарность доли положительного класса до сплита и предупреждать при различии в разы | **до обучения** |
| N4 | Считать связь каждого признака с таргетом по временным окнам и предупреждать о смене знака или силы | **до обучения** |
| N5 | Перед выводом об изменении зависимости проверять пересечение поддержки признака и стратифицировать по основным категориальным осям | автоматически |
| N6 | Сверять эмпирическую силу связи с объявленной доступностью: сильная связь у признака, объявленного недоступным, — ошибка объявления либо данных | автоматически |
| N7 | При обнаруженном дрейфе прогонять обучение на нескольких окнах истории | при дрейфе |
| N8 | Предлагать монотонные ограничения для признаков с устойчивым доменным направлением | требует объявления (§5) |
| N9 | Сравнивать ранжирование до и после калибровки и предупреждать о потере разрешающей способности | автоматически |
| N10 | Строить разбор смещения по всем категориальным признакам достаточного объёма, ранжируя сегменты по величине смещения, а не по объёму | автоматически |

N3 и N4 обязаны срабатывать **до** обучения. Дрейф, найденный после недоумения
по поводу метрик, стоит часов; найденный до обучения — минут.

N10: общая метрика не показывала, что северо-восточные штаты переоценены втрое.

## 5. `protocol/` — учёт расхода выборок

Раздела с таким содержанием в концепции не было. Он появился из самой дорогой
ошибки этапа.

| # | Требование | Статус |
|---|---|---|
| P1 | **Вести учёт обращений к каждой выборке и отказываться считать метрику на выборке, уже участвовавшей в выборе хотя бы одного решения** | **блокирующее** |
| P2 | Фиксировать, на основании какой выборки принято каждое проектное решение, и помечать решения, принятые после просмотра оценочной выборки | автоматически |
| P3 | При обнаруженном дрейфе требовать скользящей оценки по нескольким окнам и отказываться выдавать вердикт по одному | **блокирующее при дрейфе** |
| P4 | Считать интервал для разницы между кандидатами и для экономического эффекта по умолчанию, а не точечные оценки | автоматически |
| P5 | Оценивать проектные решения на окнах, не участвовавших в их выборе, показывая устойчивость знака эффекта по окнам | автоматически |
| P6 | Хранить историю заключений вместе с протоколом, при котором каждое получено | автоматически |

Цена нарушения P1 измерена: вывод перевернулся трижды, и каждый раз из-за
протокола, а не новых данных.

Цена нарушения P3 измерена: тестом оказалось единственное из пяти окон, где
картина обратная общей.

P6 — следствие обоих: заключение, менявшееся трижды, заслуживает иного доверия,
чем полученное один раз, и это должно быть видно читателю отчёта.

## 6. Что не автоматизируется никогда

Инструмент задаёт вопрос и ждёт ответа. Умолчание здесь опаснее отсутствия.

- Порядок событий процесса во времени (в данных его нет нигде).
- Доступность признака в момент решения.
- Estimand: что именно предсказывается.
- Трактовка отсутствия события.
- Цена ошибки каждого типа.
- Доменное направление зависимости для монотонных ограничений.

Все шесть — вопросы к людям, а не к данным. Они и составляют содержание
чек-листов первой недели на новом месте.

## 7. Наблюдения, не ставшие требованиями

Встретились однократно либо специфичны для Olist. Записаны, но в этап 1 не идут.

- Совместимость версий трекинга экспериментов (MLflow перевёл файловый бэкенд в
  режим поддержки). Инфраструктурная деталь, а не свойство задачи.
- Согласованность статуса и временной метки события (A5) наблюдалась на 8
  строках. Требование сформулировано, но подтверждено одним случаем.
- Немонотонность чувствительности к цене ошибки как признак непереносимости
  порога — наблюдение интересное, но выведено из одного окна.

## 8. Расхождение с концепцией

### Наблюдено, но концепцией не предвидено

| Наблюдение | Почему концепция промахнулась |
|---|---|
| Учёт расхода выборок (P1–P2) | Концепция защищала только Gold Set от контаминации. Оказалось, что валидация расходуется так же, и обращение к тесту для выбора порога — та же ошибка |
| История заключений с протоколом (P6) | Не предполагалось, что вывод может перевернуться трижды без новых данных |
| Скользящая оценка как условие вердикта (P3) | Дрейф в концепции относился к мониторингу продакшена, а не к протоколу оценки |
| Определение метки порождает лик (C6) | Концепция искала лик в данных. Здесь он возник в формуле таргета |
| Грануляция временных колонок (A10) | Не предполагалось, что дата и момент времени в одной таблице сравниваются молча |
| Калибровка теряет разрешающую способность (N9) | Предполагалось, что калибровка на ранжирование не влияет |

### Предвидено концепцией, но не наблюдалось

| Требование концепции | Почему не проявилось |
|---|---|
| Учёт множественных сравнений | Итеративного скана сегментов не было. Проявится в диагностической ветке, не в предиктивной |
| Claim–evidence entailment | Отчёт писал человек, а не LLM. Проявится при появлении LLM-слоя |
| Продольная верификация point-in-time | Работа шла с выгрузкой, наблюдать источник во времени было нечего. Уровень доказательства остался «утверждение владельца» |
| Ablation как triage лика | Не понадобился: объявленная доступность плюс эмпирическая проверка связи закрыли задачу |
| Domain Packs как хранилище типовых KPI и playbooks | Не понадобились ни разу. Здесь концепция v2 уже была права, отказавшись от них |

### Поправка: вывод о Domain Packs был неверен

Первая редакция этого документа заключала, что Domain Packs не нужны вовсе, раз
ни одно трение не потребовало доменного знания. Вывод неверен по двум причинам.

**Первая: доменное знание применялось, но не фиксировалось как таковое.**
Минимум пять решений этапа 0 опирались на знание того, как устроена
e-commerce-торговля, и были записаны как «заполнил вручную»:

| Решение | Что это на самом деле |
|---|---|
| Порядок событий: покупка → одобрение → перевозчик → доставка | знание процесса фулфилмента |
| Отменённый заказ не является опоздавшим | знание того, что обещание доставки относится к намерению доставить |
| `payment_installments` известен при оформлении, `review_score` — нет | знание последовательности чекаута |
| Направление монотонной связи: жёстче обещание — выше риск | доменный prior о логистике |
| Сам выбор таргета как осмысленной бизнес-задачи | знание отрасли |

Новичок в отрасли не ответит ни на один из этих вопросов. Я ответил мгновенно и
принял скорость ответа за отсутствие вопроса.

**Вторая: §6 этого документа уже описывает Domain Pack, не называя его.** Шесть
пунктов «что не автоматизируется никогда» — это и есть дизамбигуирующие вопросы,
которые концепция v2 определяет как ядро Domain Pack. Этап 0 вывел его из
наблюдения и тут же объявил ненужным, потому что сравнивал с отвергнутой ранее
версией — хранилищем типовых KPI.

**Исправленный вывод.** Domain Pack в форме «eval-кейсы + дизамбигуирующие
вопросы + priors как варианты» нужен, и этап 0 фактически произвёл его первую
версию для e-commerce: шесть вопросов из §6 плюс пять решений из таблицы выше.
Хранилище типовых KPI и playbooks по-прежнему не нужно.

Для гипотезы H1 это меняет формулировку: доменно-независимы оказались
**проверки**, а не **вопросы**. Проверки едут между отраслями без изменений;
вопросы к людям в каждой отрасли свои, и именно они составляют пакет.

## 9. Приоритет для этапа 1

Порядок выведен из цены нарушения, а не из удобства реализации.

**Первым — `protocol/`.** Раздела не было в концепции, а он оказался дороже
всего: пятая часть времени и три разворота вывода. P1 и P3 блокирующие.

**Вторым — блокирующие проверки `audit/`:** A8 (fanout при суммировании) и A10
(грануляция временных колонок). Обе ловят ошибки, которые выглядят правдоподобно
и потому доходят до прода.

**Третьим — контракт C1–C7.** Без объявленной доступности и estimand остальные
проверки не на чем основывать.

**Четвёртым — остальной `audit/`,** затем `analysis/`.

**Пятым — Domain Pack для e-commerce** в форме списка вопросов, а не хранилища
знаний. Материал уже есть: шесть пунктов §6 плюс пять решений из таблицы в §8.
Стоит дёшево и служит проверкой формата до появления второго домена.

**Не строить в этапе 1:** LLM-слой, учёт множественных сравнений, продольную
PIT-верификацию. Не наблюдались на этом кейсе.
