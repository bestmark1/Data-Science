## Рамка, в которой читать карту

Решения владельца 30 сентября (вопросы 1–4 раунда про техники):

1. **Инструмент ловит ошибки применения техник, а не реализует их.** Технику
   ядро реализует только там, где проверке нужен эталон для сравнения. Строить
   модели — дело построителя проекта.
2. **Пересэмплирование по умолчанию не применяется.** Если объявлено — только
   внутри обучающей части и с перекалибровкой на отдельном окне. Измерение
   дополняется PR-AUC относительно доли класса и порогом по стоимости ошибок.
3. **Uplift откладывается до рабочей задачи**, требования записываются в
   backlog (DS-009).
4. **Порядок:** довести PR #2 → DS-008 (PR-AUC и порог по стоимости в
   `measure.py`, правило о пересэмплировании в `AGENTS.md`) → кейс 21.

Два ограничения проекта отсекают часть «стандартных» практик намеренно:

* **в кейсах нет подбора гиперпараметров** — настройки фиксируются до прогона;
  в рабочем проекте подбор разрешён, но только вложенный и по времени;
* **случайного K-fold нет в штатном API** — `split_by_windows` строит части
  только по времени. Произвольный код построителя этим API механически не
  ограничен.

### Статусы

Статус описывает одно: что есть и какой ценой это держится.

* **код** — реализовано в ядре, указано где; ограничения названы в той же
  строке;
* **диагностика** — код сигнализирует о проблеме, но не устраняет её и не
  строит правильный вариант;
* **правило** — записано в `AGENTS.md` или протоколе, автоматически не
  проверяется;
* **нет** — отсутствует; если есть предложение, указан кандидат из «Итога»;
* **вне области** — не нужно, пока нет задачи этого типа.

Приёмка отдельно: всё помеченное «код» проверено тестами и стендом, если не
сказано иначе. DS-004 (аналоги) — на независимой проверке, статус `review`.

## 3. Разбиение и валидация

Три разные вещи, которые первая редакция смешивала: **построение частей** (ядро),
**измерение готовых прогнозов** (ядро) и **переобучение модели по окнам**
(построитель).

| Техника | Статус | Где и граница |
|---|---|---|
| Части train / evaluate по времени и резерв | код | `split_by_windows`: expanding train, в него допускаются только метки, известные до начала окна; отдельного объекта validation нет |
| Сравнение с правилом по окнам | код | `stability_across_windows` (N7) меряет ГОТОВЫЕ прогнозы по окнам и сам не переобучает. Это не rolling CV |
| Переобучение отдельной модели на каждом окне | нет в построителях | в `subscription-churn` и `nys-wc-claims` одна модель, обученная на train последней части, оценивается во всех окнах; оценочные строки ранних окон входили в её обучение. Долг записан в handoff |
| Purge перекрытия окон признаков | код | `purge_overlapping_train`, `FeatureWindowOverlap`: для объявленных окон и повторных объектов |
| Незрелые метки в оценочных частях и резерве | диагностика | `LabelImmaturity` (A12) сигнализирует о доле незрелых; зазора не создаёт. Отдельного embargo нет |
| Групповая зависимость, пересечение сущностей | диагностика | `GroupDependence` (N14), `EntityOverlapAcrossSplits` находят пересечения; группового разбиения не строят |
| Защита резерва | код, узкая | `SampleLedger` запрещает повторное итоговое измерение и измерение после зарегистрированного выбора. `AUDIT` отдаёт кадр без расхода; честность назначения обращения и фактического использования данных — граница механизма |
| Вложенная кросс-валидация для подбора | вне области кейсов | рабочий проект, кандидат В |
| Многомерная различимость периодов (adversarial validation) | нет | кандидат Б. `ComparableSupport` сравнивает диапазоны по одному признаку |
| Единица bootstrap при зависимых объектах | нет | `measure.py` пересэмплирует строки; для зависимых объектов достаточность не установлена (REFORMS) |

## 11. Причинный вывод и uplift

Решение 3: откладывается до рабочей задачи. Требования для DS-009:

* **идентификация:** рандомизированный эксперимент или, для наблюдательных
  данных, явно названные предпосылки — отсутствие скрытых смешивающих,
  перекрытие групп (overlap), отсутствие взаимного влияния единиц
  (interference); флаг воздействия — объявленная роль в формуляре;
  `TargetKind.UPLIFT` есть в перечне, но не в `SUPPORTED`;
* **проверки до модели:** перекрытие распределений групп; доля групп совпадает
  с объявленной (sample ratio mismatch); признаки после воздействия запрещены;
* **модели:** мета-обучатели S/T/X, DR-learner, causal forest; причинные
  foundation-модели — претенденты (раздел 14); библиотеки — по согласованию;
* **измерение:** точность эффекта и полезность политики — разные цели;
  мерить политику назначения (прибыль при бюджете) несколькими метриками с
  интервалом; Qini неустойчив при смещении отбора, Uplift и AUUC устойчивее
  (раздел 14); разбиение по времени;
* **стенд:** миры с известным эффектом и с эффектом, подменённым отбором.

### Foundation-модели: чужой лидерборд не заменяет наше сравнение

* **BeyondArena** (июнь 2026): 21 временной набор из 142. Временное разбиение —
  отсечка по дате с горизонтом прогноза; **зазора под созревание метки нет**.
  Классические модели, включая бустинг и RealMLP, **настраиваются** (25
  конфигураций случайного поиска и ансамбль), foundation-модели — нет. Числа
  отдельно по временной бинарной классификации не табулированы; есть агрегат,
  где foundation-модели уступают на не-IID и крупных данных. Ошибка
  foundation-моделей заметно растёт примерно от 100 тысяч строк.
* **Для нашего протокола это не прямое свидетельство.** У нас подбор в кейсах
  запрещён, а там бустинг получил подбор. Честное сравнение в нашей постановке —
  две колонки: без подбора и с подбором, равным по бюджету. Зазор под
  созревание метки у нас уже есть: `split_by_windows` допускает в train только
  метки, известные до начала окна (`split.py:195`).
* **OOD-работа** (июль 2026) **временного сдвига не содержит**: сдвиг меток,
  подгрупп и географии. О нашей постановке она не говорит; первая редакция
  карты ошибочно приводила её как довод о времени.
* **Отчёт TabPFN-3.5**: на подмножестве до 100 тысяч строк сопоставим с
  лучшими, на полном временном и групповом наборе ансамбли MLP сохраняют
  преимущество. Калибровка сырых вероятностей 3.5 не опубликована — мерить
  самим. Без GPU медленно.

Вывод прежний: **выбирать модель по чужому лидерборду нельзя; сравнивать на
нашем разбиении по времени при равном бюджете подбора.** Кандидат И.

объявлено некоммерческим. В рабочем проекте, где выходы идут в решения
работодателя, — пересмотреть до применения.

### Для ядра: методы и их условия

| Метод | Вид гарантии | Требования | Годится ли проекту |
|---|---|---|---|
| CBPE | оценка метрики без меток | калиброванная модель; только сдвиг ковариат, смена связи — провал идентификации, а не просто неточность | реализация NannyML, Apache-2.0; ROC AUC поддержан, **PR-AUC не найден** — а DS-008 вводит именно его |
| PAPE | то же с поправкой калибровки на сдвиг ковариат | условия переноса, общий носитель, оценка отношения плотностей | готовой библиотеки не найдено |
| PPI++ | интервал по малому числу меток, асимптотический | размеченные и неразмеченные — из одной совокупности | **в постановке «старые метки → свежие окна» не годится** (пример ревью: оценка 0.1 при истинном 0.8) |
| Generalized PPI (февраль 2026) | то же для любой регулярной асимптотически линейной оценки, в том числе TPR, FPR, AUC | три формы сдвига ковариат; смена связи не покрыта | ближе всего к нашей постановке; кандидат Е |
| Conformal risk control | контроль ожидаемого монотонного риска, в том числе доли пропусков (FNR) | обменяемость калибровочных и будущих строк | FNR монотонна — гарантия возможна; стоимость ошибок в общем случае немонотонна. При разбиении по времени обменяемость не обеспечена, созревание метки метод не решает. MAPIE 1.4.1: `BinaryClassificationController` |
| ACI | частота ошибок во времени, асимптотически | онлайн-поток; задержанная обратная связь — открытая задача у авторов | исследование |
| Мультикалибровка | калибровка по семейству подгрупп | прогнозы меняются | MCGrad (Meta, KDD 2026, в эксплуатации на сотнях моделей); лицензия MIT по словам агента, не перепроверена. Кандидат Д2 |
| Anytime-valid вывод | повторные взгляды без роста ошибки | последовательная конструкция (e-process) | `validanytime-detectors` — локально, Apache-2.0; `expectation` — предварительная версия, лицензия не подтверждена; облачный SDK исключён: данные не покидают машину |
| Генератор миров из случайных причинных моделей | разнообразие миров | своё априорное распределение со своими ограничениями | априорный генератор TabICLv2 (`graph_scm`) открыт; у Drift-Resilient TabPFN — меняющаяся во времени причинная модель, то есть готовые миры со сменой связи; генератор TabPFN не опубликован. Кандидат Ж |
| Статический анализ утечек в коде (абстрактная интерпретация, 2024–2025; LeakageDetector 2.0) | доказательство отсутствия утечки train/test до обучения | анализ проверен на ноутбуках Jupyter | закрывает пробел «где обучена предобработка» (L1.2) в коде построителя; применимость к нашим скриптам не проверена. Кандидат К |

**Названный предел.** Сочетание сдвига во времени, отложенной метки и
повторного наблюдения не закрывает ни один метод по отдельности: ни
BeyondArena, ни CBPE/PAPE, ни PPI, ни conformal. Применять их как
взаимозаменяемые «методы без свежей метки» — методическая ошибка.

### Для uplift (DS-009)

* **Причинные foundation-модели** выигрывают не везде: на RealCause-Lalonde
  средний ранг PEHE у T-learner 1.40 против 1.75 у CausalPFN (меньше лучше);
  в CausalFM на ACIC2016 PEHE у X-learner 0.519 против 0.638. CausalFM
  поддерживает поправки back-door, front-door и через инструментальную
  переменную — у каждой свои предпосылки. Код CausalFM Apache-2.0, лицензия
  весов не найдена; проверки при сдвиге во времени нет.
* **Точность эффекта и качество решения — разные цели.** Оценщик, лучший по
  ошибке эффекта, тратит точность там, где знак решения и так ясен; для
  политики важны ошибки у границы решения. Предложена переориентированная
  двухшаговая цель (2025).
* **Qini неустойчив** при смещении отбора и скрытом смешении: его
  масштабирование на соотношение групп усиливает ошибку при их дисбалансе.
  Uplift и AUUC устойчивее в ранжировании моделей. Рекомендация авторов —
  несколько метрик сразу, согласованных со средним эффектом (KDD 2026).

**Правило претендента в редакции после ревью.** Заранее фиксируются претендент,
метрика и разбиение. Считается интервал bootstrap **разницы метрик на
одинаковых строках**, как в `measure_contrast`. Преимущество засчитывается,
если нижняя граница разницы выше заранее объявленного минимального полезного
улучшения, не ниже нуля; для функций потерь направление обратное. Единица
bootstrap — по структуре зависимости. Несколько претендентов по итоговому
резерву не отбираются. Бюджет подбора у претендента и действующей модели
равен и объявлен заранее: в кейсе — без подбора у обоих.
