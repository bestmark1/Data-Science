# Консолидированное архитектурное ревью

Свод трёх независимых разборов концепции Adaptive AI + Data Science Platform с разрешёнными противоречиями. Это вход в MRD.

Источники:
- [ARCHITECTURE_REVIEW.md](ARCHITECTURE_REVIEW.md) — ревью №1 (Claude Opus 5)
- [QWEN_REVIEW.md](QWEN_REVIEW.md) — ревью №2 (Qwen 3.8 max)
- [CODEX_REVIEW.md](CODEX_REVIEW.md) — ревью №3 (Codex, gpt-5.6-sol)
- [CONCEPT_SUMMARY.md](CONCEPT_SUMMARY.md) — исходная концепция

Контекст: соло-разработка, в первую очередь для себя, возможная публикация в открытый доступ позже. Корпоративного хранилища, продакшена и реальных бизнес-решений сейчас нет. Требование автора — домен-агностичная заготовка, пригодная для любой отрасли.

---

## 1. Что это за система на самом деле

Три ревью сошлись на том, что исходное позиционирование неверно. Итоговая формулировка:

> Это **локальный компилятор аналитического контракта в воспроизводимую цепочку claims и evidence**.

Не универсальная DS-платформа, не набор адаптеров, не агент-аналитик. Data Readiness, LLM-планирование и Domain Packs — проверяемые расширения вокруг устойчивого центра, а не конкурирующие центры архитектуры.

Практическое следствие: если убрать LLM целиком, система должна остаться полезной. LLM ускоряет заполнение контракта и формулирование выводов, но не является несущей конструкцией. Система, которая без LLM превращается в тыкву, построена неправильно.

## 2. Центральный объект: Analytical Contract

Главная находка Codex, пропущенная двумя первыми ревью: после сокращения объёма в архитектуре **не осталось главного** — типизированного представления между вопросом и SQL.

Без него система остаётся LLM-оркестратором над SQL с хорошими логами.

### 2.1 Почему это критично

Если LLM сразу пишет SQL, а валидатор проверяет готовый запрос, **большинство смысловых ошибок уже неотличимы от корректных решений**. Запрос, посчитавший метрику по неверной когорте, синтаксически безупречен и проходит любую проверку схемы.

Валидировать надо контракт, а не результат.

### 2.2 Последовательность

```
вопрос
  → Analytical Contract (типизированный, валидируемый)
  → исполнимый план
  → результаты инструментов
  → claims, связанные с evidence
```

### 2.3 Минимальный состав контракта

Не пытаться описать всю статистику. Начать с того, что порождает большинство ошибок:

```
population        — исследуемая популяция и eligibility
grain             — единица наблюдения
entity_keys       — и правила identity resolution
metric_version    — ссылка на версионированное определение
as_of             — + timezone, календарь, границы полного периода
baseline          — с чем сравниваем
exposure          — intervention, если есть
outcome           — + горизонт наблюдения
estimand          — что именно оценивается
assumptions       — явный список
computation_plan  — план вычислений
claim_evidence    — граф связей вывод ← доказательство
epistemic_status  — descriptive / predictive / causal + uncertainty
```

Это центральный API системы, а не ещё один advisor. Он появляется **до** агента.

## 3. Разрешение противоречий между ревью

Тринадцать точек расхождения и принятые решения.

### 3.1 Домен-агностичность vs ограничение семейства задач

**Расхождение.** Требование автора — любая отрасль. Codex: отрасль не главная ось различия, разрушительнее batch vs streaming, классификация vs survival, таблицы vs графы.

**Решение — это не противоречие, а разные оси.** Система **домен-агностична** (отрасль — декларативный файл) и одновременно **ограничена по семейству задач**: batch-аналитика над табличными и event-данными с явной временной осью.

Streaming, survival analysis, графы, мультимодальность — отдельные execution profiles, вне текущей области. Ограничение объявляется явно, а не подразумевается.

Без этого второй домен проверит не переносимость ядра, а отсутствие поддержки другой вычислительной парадигмы.

### 3.2 Сколько доменов в MVP

**Расхождение.** Qwen: один. Claude: два максимально далёких. Codex: обе крайности неверны.

**Решение — Codex, по одной оси за раз.** Два далёких домена сразу смешивают пять переменных: домен, модальность, тип задачи, временную структуру, способ валидации.

```
1. anchor domain (e-commerce/marketplace — быстрая обратная связь, естественные метки)
2. второй use case внутри него         ← первая проверка переносимости
3. тот же тип анализа во втором домене ← вторая проверка, одна новая переменная
4. другая модальность                  ← только после стабилизации
```

Второй домен — не второй полноценный продукт, а conformance-тест границы.

**Критерий H1 пересмотрен.** Мой исходный критерий «тронул `core/` — абстракция провалилась» отвергнут как слишком строгий для ранней стадии: второй кейс и нужен, чтобы починить плохую абстракцию. Провал — это `if domain == ...` в ядре и постоянные breaking changes **после** стабилизации.

### 3.3 Point-in-time correctness

**Расхождение.** Claude: проверяется только продольно, хэш-диф партиций, демон с дня 1. Codex: тезис одновременно слишком сильный и недостаточный.

**Решение — иерархия доказательств Codex.**

| Уровень | Основание | Сила |
|---|---|---|
| 1 | Immutable event log / transaction-time / bitemporal history + versioned transformation | сильное |
| 2 | Snapshots, warehouse time travel, CDC с retention, ingestion logs | среднее |
| 3 | Утверждение владельца + schema heuristics | слабое |
| 4 | Longitudinal hash-diff | мониторинг мутабельности, **не** доказательство PIT |

Хэш-диф показывает, что содержимое изменилось. Он не доказывает, когда значение стало доступно, что партиция не была сразу построена с использованием будущего, что pipeline применял корректный `as_of`, и что поле не post-treatment.

Утверждение «не запустил демона в день 1 — не докажешь никогда» **отозвано**: обоснованная PIT-реконструкция возможна без демона, если источник уже имеет историю нужного класса.

Демон остаётся полезным как детектор мутабельности, но переезжает с уровня «архитектурная необходимость» на уровень «инструмент мониторинга».

### 3.4 Синтетические миры

**Расхождение.** Claude: «строго лучше реальных кейсов». Codex: перегиб.

**Решение — пирамида тестов, синтетика в основании.**

Системные слабости синтетики: генератор и система разделяют одну онтологию; данные чище реальных join'ов, identity и missingness; агент может выучить артефакты генератора; **известная причина может быть неидентифицируема** из доступных наблюдений; рост числа seed'ов не создаёт новых классов ошибок.

```
уровень 1  synthetic fault injection — PIT, leakage, structural breaks, negative controls
уровень 2  вручную составленные messy case bundles
уровень 3  воспроизведение известных публичных исследований
уровень 4  реальные пользовательские вопросы (позже)
```

**Критично:** нельзя оценивать причинный анализ по правилу «назвал инжектированную причину». При недостаточной идентифицируемости правильный ответ системы — «по этим данным причину установить нельзя». Иначе обучаем систему всегда находить причину.

### 3.5 Adapter-first

**Расхождение.** Claude/Qwen: adapter-first как стратегия. Codex: верная архитектура, плохой буквальный roadmap для соло.

**Решение — «integration-friendly сейчас, adapter-rich потом».** Порты, спроектированные заранее под dbt, Cube, Feast, MLflow и GrowthBook без единой реальной интеграции, будут придуманными, а матрица версий съест проект.

```
один локальный reference path
+ одна фактически нужная интеграция
→ общий порт извлекается ПОСЛЕ второго реального варианта
```

Встроенную реализацию не называть универсальным fallback, если она поддерживает узкий сценарий.

Стратегическая позиция «не строим свой feature store / experiment engine / labeling» остаётся в силе.

### 3.6 Схлопывание advisors

**Расхождение.** Qwen: 13 модулей → один Project Setup Workflow. Codex: один пользовательский workflow разумен, один неструктурированный manifest — нет.

**Решение — один workflow, четыре типизированных артефакта.**

| Артефакт | Владелец | Основание для изменения |
|---|---|---|
| Problem Statement | автор/бизнес | смена цели |
| Metric Contract | владелец метрики | смена определения |
| Decision Contract | операционный владелец | смена процесса принятия решения |
| Data Evidence | владелец данных | новые факты о данных |

Не сервисы и не агенты — логически раздельные типизированные артефакты с разными версиями, сроками жизни и правилами approval. Иначе невозможно установить, какая предпосылка изменила итог.

### 3.7 Типы знания

**Расхождение.** Qwen: пять типов → один versioned repository. Codex: физическое объединение допустимо, семантическое — нет.

**Решение — одно хранилище, типизированные режимы доверия.** Retrieved fact, human-approved definition, экспериментальный результат и гипотеза агента различаются авторитетностью, сроком жизни, допустимостью использования в рантайме и требованиями к approval. Поле `trust_mode` обязательно.

### 3.8 Gold Set

**Расхождение.** Claude: инвариант против contamination. Qwen: замороженный набор устаревает относительно прода, «полностью заморожен» + «непрерывное обучение» несовместимы. Codex: единый пополняемый набор быстро становится train set.

**Решение — три набора с первого дня.**

```
development set     — открытый, используется при настройке
regression set      — пополняется из провалов, human-approved
release-challenge   — неизменяемый, НЕ используется при настройке,
                      прогоняется только перед релизом
```

**Инвариант GS-1 сохраняется:** ни один артефакт, порождённый обучением, не попадает в release-challenge без подписанной человеком записи provenance. Failure case может попасть в regression, но не может задним числом подтверждать уже сделанный релиз.

### 3.9 Уровень риска

**Расхождение.** Концепция и первые два ревью: risk profile на уровне проекта. Codex: неверный уровень.

**Решение — Codex.** Один проект содержит и безопасное описательное сравнение, и рекомендацию сменить политику. Проектный `LOW/MEDIUM/HIGH` даёт либо избыточные гейты, либо пропуск опасных выводов.

Риск крепится к **claim, tool call и предлагаемому действию** и оценивается по: обратимости, blast radius, цене ошибки, времени до обнаружения ошибки, чувствительности данных, возможности независимой проверки, типу вывода (описательный / прогноз / причинная рекомендация).

Project Risk Profile остаётся как default policy, но не как окончательное решение маршрутизации.

### 3.10 Evals

**Расхождение.** Claude: 4 измерения, включая grounding чисел. Codex: grounding ловит только выдуманные числа.

**Решение — grounding необходим, но недостаточен.** Он пропускает: число посчитано для другой когорты; перепутаны числитель и знаменатель; неверная единица измерения; сравниваются неполные периоды; абсолютное изменение названо относительным; выбрано одно из двадцати сравнений; evidence истинно, но логически не поддерживает claim.

Итоговый набор:

```
1. SQL исполним против управляемой схемы            детерминированно
2. Использованы версионированные определения метрик  детерминированно
   (не AST-сравнение — см. §3.12)
3. Grounding: каждое число из трейса                 детерминированно
4. Claim–evidence entailment                         детерминированно + LLM-judge
   популяция, вычисление, направление эффекта,
   uncertainty, ограничения, тип допустимого утверждения
5. Multiplicity accounting                           детерминированно (§3.11)
6. Контракт деградации: система говорит              смешанно
   "по этим данным ответить нельзя", когда это так
```

Пункт 6 — важнейший. Пункт 4 — самый дорогой.

### 3.11 Множественное тестирование (новое, не было ни в одном первом ревью)

Агент итеративно сканирует сегменты, окна, метрики и гипотезы. Восемьдесят сравнений, два с `p < 0.05` — автоматизированный garden of forking paths. При идеально корректных SQL и формулах система систематически находит убедительные ложные причины.

Архитектура обязана различать и хранить:

```
exploratory findings
pre-specified confirmatory tests
семейство ВСЕХ выполненных сравнений
результаты после multiplicity correction / FDR
подтверждение на отложенном периоде
отрицательные результаты — не выбрасываются из трейса
```

Это, вероятно, самый частый способ, которым такая система будет ошибаться.

### 3.12 Leakage и семантическая корректность SQL

**Расхождение.** Claude: ablation как первоклассный детектор, AST-сверка с определением метрики. Codex: и то и другое создаёт ложную детерминированную уверенность.

**Решение — понизить статус обоих.**

Ablation не является сильным детектором: легитимный признак может нести большую часть сигнала; leakage может быть размазан по коррелированным признакам; дубликаты скрывают эффект удаления колонки; «слишком хорошая метрика» не имеет универсального доменного потолка. **Ablation — triage, не повышает уровень доказанности leakage без временного или семантического evidence.**

AST-сравнение не устанавливает семантическую эквивалентность. Нужны **grain/cardinality contracts, effective-dating rules и executable reconciliation tests** на контрольных данных.

**Расширение области.** Semantic layer не защищает от главных ошибок аналитического SQL: fanout после many-to-many join, двойной подсчёт событий, неверное применение SCD, расхождение user/account/device identity, смешение валют, границы дня в разных таймзонах, late-arriving facts, несовместимые grain числителя и знаменателя.

### 3.13 Leakage как частный случай наблюдаемости

Все три ревью и концепция сосредоточены на будущем в признаках. Не менее опасны: selection и survivorship bias, censoring, delayed outcomes, MNAR-пропуски, policy-induced labels, **rejection inference** (исход известен только для тех, кому уже разрешили действие), treatment contamination, interference между единицами, изменение поведения после внедрения модели, отсутствие результата, ошибочно принятое за отрицательную метку.

**Решение — отдельный Observation & Decision Contract**: почему объект попал в данные, когда результат становится наблюдаемым, какое действие уже на него влияло, для какой части популяции outcome вообще доступен.

PIT-корректный датасет может быть непригоден для поставленного вопроса.

## 4. Что сохраняется из концепции без изменений

Три ревью независимо подтвердили ценность:

- Business problem → KPI → DS problem как обязательная цепочка.
- `event_time ≠ available_at` как first-class различие.
- **Impact Chain со статусами** `hypothesized / observationally_supported / experimentally_validated / rejected`. Лучшая идея документа.
- **Статус `rejected` и хранение отрицательных результатов.** Для соло-проекта, возможно, полезнее «обучения»: не предлагать повторно уже опровергнутую связь, снижать survivorship bias.
- **Decision Moment** — Codex: более важный объект, чем Domain Pack. Выносится в отдельный Decision Contract, а не остаётся полем Target Advisor. Отсекает модели, статистически хорошие и операционно бесполезные.
- **Явные состояния доступности данных** `missing / partial / proxy / historically_unavailable` — один из немногих действительно домен-агностичных элементов концепции. Не сводить к `NOT READY`.
- **Журнал решения по structural break** `include / exclude / downweight / separate_regime / indicator`. Резать надо отдельного Advisor, а не decision record: детектор укажет дату, но не ответит, что делать.
- **Label ledger** — даже без labeling-платформы. Поля `source`, `available_at`, `guideline_version`, `annotator`, `confidence`, `adjudication` нужны для delayed outcomes, policy-induced labels и качества Gold Set.
- Разделение evals и экспериментов.
- Baseline first.
- «LLM решает что считать → tool считает → LLM интерпретирует».

## 5. Необратимые решения

Принять до первой строки кода. Поздняя смена означает переписывание, а не рефакторинг.

| # | Решение | Принято |
|---|---|---|
| 1 | **Семейство задач** | Batch-аналитика над табличными и event-данными с явной временной осью. Streaming, survival, графы, мультимодальность — отдельные execution profiles, вне области |
| 2 | **Каноническая модель анализа** | Типизированный Analytical Contract + claim–evidence graph, вводится до агента. Начать с grain, cohort, time, metric, comparison, estimand, assumptions |
| 3 | **Временная модель** | Канонически различать `event_time`, `source_available_at` (с состоянием `unknown`), `ingested_at`, validity interval, snapshot ID. Полная битемпоральность от каждого источника **не** требуется |
| 4 | **Модель артефактов** | Все входы, контракты, результаты инструментов и отчёты — immutable / content-addressed. `latest` только алиас. Основа replay, lineage и удаления ошибочного знания |
| 5 | **Граница расширений** | Domain Packs и eval packs — **только versioned data**. Исполняемые tools — отдельный capability API с явным доверием. Исполняемые паки запрещены |
| 6 | **Разделение eval-наборов** | development / regression / release-challenge с первого дня |
| 7 | **Модель развёртывания** | Локальное single-user приложение. Hosted multi-tenant — отдельная архитектура, а не «режим, который добавим позже» |

Решение 7 снимает вопрос RLS и мультиарендности: не «решать на старте», а честно объявить вне области. Опасно делать вид, что локальное приложение позже безопасно превращается в multi-tenant добавлением логина.

Решение 5 критично именно для планов на опенсорс: если ради удобства разрешить исполняемые паки, отделить данные от кода без слома публичного формата будет невозможно.

## 6. Что вне области

Явный отрицательный scope. Не «потом», а «не в этом продукте».

**Не строим** (используем существующее или не используем вовсе): feature store, experiment engine, labeling-платформа, data contract system, observability-стек, multi-agent runtime, собственный semantic layer с нуля.

**Не делаем в обозримом плане**: Learning Engine с петлями обучения, Execution Router как обучаемый компонент, multi-model orchestration, independent LLM reviewer как контрольный механизм, мультимодальность, autonomous updates семантического слоя и метрик, production action execution.

**Не поддерживаем**: регулируемые домены (healthcare, credit, employment, insurance). Это не флаг `risk=HIGH`, а SR 11-7, ECOA adverse action, EU AI Act и HIPAA — другой продукт. Extension point оставить, обещаний не давать.

**Гейты**: Data Readiness не блокирует. Он производит подписанную запись о рисках и различает `verified / contradicted / unknown`, а не `READY / CONDITIONAL / NOT READY`. Настоящих блокеров три: доказанный временной лик, контаминация release-challenge set, PIT-ненадёжность при необратимом действии.

## 7. Порядок работ

Восемь этапов. У каждого — работающий артефакт и критерий честной остановки. Агент появляется только на этапе 3.

### Этап 0 — зафиксировать отрицательный scope
**Артефакт:** одностраничный контракт продукта: один пользователь, одно семейство задач, локальные версионированные датасеты, никакого исполнения действий в проде.

**Стоп:** если нельзя назвать один повторяющийся собственный сценарий, который вы реально выполняете несколько раз — платформу строить не нужно.

### Этап 1 — eval substrate, не большой генератор миров
**Артефакт:** 12–20 case bundles: несколько чистых детерминированных, fault-injection, **no-signal controls**, messy ручные. Для каждого — ожидаемые evidence и допустимые/недопустимые claims. Одновременно зафиксировать baseline: обычная LLM с теми же данными и инструментами, либо ваш ручной анализ.

**Стоп:** если рубрика не отличает хороший ответ от правдоподобного, или baseline уже решает задачи приемлемо — гипотезы не подтверждены.

### Этап 2 — детерминированный evidence runner без агента
План анализа заполняется вручную.

**Артефакт:** воспроизводимый отчёт из pinned dataset, версий определений метрик, Analytical Contract, результатов инструментов, claims и lineage.

**Проверка:** повторный запуск даёт тот же результат; проверки fanout, периода и grain ловят заранее заложенные ошибки.

**Стоп:** если ручное заполнение контракта не делает отчёт полезнее ноутбука — платформа не нужна, достаточно библиотеки или шаблона.

### Этап 3 — один LLM-проход: планирование и формулировка claims
LLM преобразует вопрос в Analytical Contract. Не меняет вычисления, не выбирает права доступа.

**Артефакт:** вопрос → проверяемый план → evidence report → ограниченный вывод.

**Проверка:** слепое сравнение с baseline по критическим ошибкам, времени и числу ручных исправлений.

**Стоп:** если LLM-планировщик не уменьшает число смысловых ошибок, или ускорение съедается проверкой его плана — оставить детерминированный runner.

### Этап 4 — Data Readiness как fault-detection report
Начать не со сводного score, а с временной доказательности, grain, joins, observability меток, целостности сплита и списка вопросов, не решаемых автоматически.

**Артефакт:** отчёт различает `verified / contradicted / unknown`.

**Стоп:** если система в основном генерирует общие вопросы, а не находит конкретные дефекты — H3 сводится к хорошему чек-листу, его и оставить.

### Этап 5 — три собственных исследования без правки ядра под каждый кейс
**Артефакт:** минимальный Setup Workflow, **извлечённый** из фактической работы, а не спроектированный заранее.

**Стоп:** если вы сами обходите workflow или заполняете манифесты задним числом — публичные пользователи тем более не будут.

### Этап 6 — переносимость по одной оси за раз
Второй use case в anchor domain → тот же тип анализа во втором домене → другая модальность.

**Артефакт:** conformance report: какие контракты и инструменты переиспользованы, какие расширены.

**Стоп:** если появляются `if domain == ...` в ядре или требуется новый смысл базовых сущностей — H1 сужается до task-specific toolkit.

### Этап 7 — одна learning-операция вручную
`failure → diagnosis → regression candidate → human acceptance → новая версия eval suite → release report`.

**Артефакт:** контролируемый update и rollback без Learning Engine.

**Стоп:** если вы не поддерживаете этот процесс на собственных ошибках — у H7 нет операционного владельца.

### Этап 8 — только после повторного личного использования готовить OSS
Публиковать не «платформу», а: reference runner, схемы контрактов, несколько case bundles, один reference adapter, документацию о границах применимости.

## 8. Статус гипотез

| Гипотеза | Проверяема соло | Где проверяется |
|---|---|---|
| H1 reusable core | **да**, в пересмотренной формулировке | этап 6, по одной оси |
| H2 business → DS цепочка | **частично** | этапы 3, 5. Полностью — только с реальными решениями |
| H3 data reliability | **да** | этап 4, сильнейшая часть |
| H4 label efficiency | нет | нужна реальная разметочная операция |
| H5 adaptive orchestration | нет | неизмеримо без объёма и разметки исходов |
| H6 experimentation | нет | нет продакшена → нет каузального сигнала |
| H7 controlled learning | **частично** | этап 7, одна операция вручную |
| H8 end-to-end loop | нет | цикл не замыкается без продакшена |

Честная оценка: соло проверяются вычислительная корректность и переносимость. Продуктовые обещания H2, H6–H8 целиком подтвердить нельзя — только на первом реальном внедрении.

## 9. Структурная ошибка оценки

Вы одновременно разработчик, пользователь и судья. Вы знаете устройство синтетических миров, ожидаемые причины и слабости системы, а затем сами пишете промпты и оцениваете ответы. Оптимизация под собственную онтологию произойдёт без намеренного оверфита.

Частичное лечение, не требующее компании:

```
1. открытые development fixtures
2. неизменяемые challenge cases, не используемые при настройке
3. независимые messy cases из публичных данных и опубликованных разборов
4. несколько кейсов, сформулированных другим человеком без ваших подсказок
```

## 10. Открытые вопросы для MRD

Требуют вашего решения, не выводятся из ревью:

1. **Anchor domain** — e-commerce/marketplace по умолчанию (быстрая обратная связь, естественные метки, публичные данные). Подтвердить или заменить на домен, в котором у вас есть собственный повторяющийся сценарий. Второй важнее первого: этап 0 требует **вашего** реального сценария.
2. **Источник данных для anchor domain** — публичный датасет, синтетика или ваши данные.
3. **Язык и стек** — влияет на решение 4 (content-addressed артефакты) и на порог входа для будущих контрибьюторов.
4. **Формат Analytical Contract** — YAML/JSON со схемой против внутреннего DSL. Влияет на решение 5 (данные против кода).
5. **Глубина статистики на старте** — какой минимум тестов и оценок uncertainty поддерживать в этапе 2.
6. **Срок до этапа 3** — если LLM-проход не появится в разумный срок, проект остаётся аналитической библиотекой. Это допустимый исход, но его надо признать заранее.
