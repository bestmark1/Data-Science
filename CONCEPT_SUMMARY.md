# КОНЦЕПЦИЯ (сжатое изложение)

Предлагается построить переиспользуемое ядро "Adaptive Analytics / Data Science Agent Core" — одна платформа вместо отдельных AI-агентов под каждый DS-проект. Адаптация под проект идёт через конфигурацию: Project Config, Domain Pack, Risk Profile, Business Context, Metric System, Semantic Layer, Data Sources, Data Contracts, Knowledge Base, Tools, Models, Playbooks, Evals, Experimentation Config, Project Memory, Learned Knowledge.

Слои: Orchestration / Execution / Observability → Project Context → Domain Pack + Semantic Layer + Metrics + Data Layer + Knowledge/Models → Analytics Agent → Evaluation → Experimentation → Learning Engine.

Заявленные принципы (25 штук), ключевые: business-first не model-first; semantic layer до автономной аналитики; data readiness до моделирования; point-in-time correctness как first-class; evidence before conclusion; детерминизм где возможно, LLM только для планирования/интерпретации/гипотез/оркестрации; не каждый проект требует ML; minimal sufficient agentic complexity; multi-agent и multi-model только при измеримом эффекте; review пропорционален риску; offline metric ≠ business impact; agent eval ≠ business impact; causal validation в проде; continuous learning контролируемый, версионированный, обратимый; production failures превращаются в regression evals; critical knowledge не переписывается LLM автоматически; любое learned knowledge имеет provenance; data leakage — блокирующая проблема; Gold Set защищён от contamination; любая рекомендация объяснима.

Domain Packs: каталог из 20 доменов (e-commerce, marketplace, SaaS, retail, adtech, fintech, banking, insurance, healthcare, telecom, manufacturing, logistics, energy, cybersecurity, travel, real estate, media, gaming, HR, custom). Каждый Pack даёт priors: типовые бизнес-цели, KPI, metric trees, диагностические метрики, guardrails, leading/lagging индикаторы, семантические концепты, типовые DS-задачи, типовые таргеты, типовые model metrics, требования к данным, типовые риски лика, паттерны экспериментов, playbooks, регуляторные ограничения.

Risk Profile (LOW/MEDIUM/HIGH) влияет на: автономность, требования к ревьюеру, multi-model, human approval, порог доказательности, права на инструменты, требования к экспериментам, права на обучение, логирование, аудит.

Полный lifecycle из ~28 стадий: Business Problem → Objective → KPI/Metric System → Semantic Definitions → Analytical/DS Problem → Target + Decision Moment → Data Requirements → Data Availability → Data Readiness → Point-in-time/Leakage Validation → Data Period/Seasonality → Label Quality → Data Acquisition/Labeling → Data Sufficiency → Gold Eval Set → Data Readiness Gate → EDA → Baseline → Statistics/ML → Offline Model Eval → AI/Agent Layer → Agent Evals → Pre-prod Validation → Online Experiment/Causal Validation → Business KPI Impact → Ship/Iterate/Reject → Production Monitoring → Feedback → Continuous Learning → Versioned Update. Lifecycle должен ветвиться по типу задачи (диагностической аналитике не нужны target/ML/labeling).

AI-assisted Project Setup Wizard — не анкета, а система problem framing: пользователь может не знать, какой KPI, target, нужен ли ML, какие данные, какая model metric, какой эксперимент. AI предлагает и объясняет reasoning. Внутри — цепочка советников: Domain Advisor, Business Problem, Metric Advisor (primary KPI / diagnostic / guardrail / leading / lagging + metric trees + формальные metric definitions с версионированием и valid_from/valid_to), Semantic Layer (бизнес-смысл данных, приоритет над догадками LLM), Business→DS Problem mapping, Target Advisor (target, label, observation/label window, horizon, decision moment, actionability, delayed outcomes, imbalance, leakage risks), Prediction/Decision Moment как часть конфига, Data Requirements Advisor, Data Availability (available/missing/partial/proxy/historical unavailable).

Data Readiness Layer: availability, completeness, consistency, temporal integrity, leakage, historical coverage, seasonality, label quality, sample sufficiency, representativeness. Point-in-time correctness: для каждого обучающего наблюдения восстановить состояние данных на момент предсказания. Feature metadata: event_time, available_at, valid_from, valid_to, update_frequency, is_mutable, snapshot_available, leakage_risk. Mutable data detection (append-only? overwrite? history tables? snapshots? CDC? event sourcing?) → вердикт о надёжности PIT-обучения. Retrotests/historical snapshots. Leakage control (future info, target-derived features, post-treatment variables, агрегаты через момент предсказания, перезаписанная история, train/test contamination, preprocessing на всём датасете, entity leakage, temporal leakage) + детерминированный Leakage Validator с частью правил как ERROR/WARNING, но с оговоркой что автоматика не заменяет domain review. Split Advisor (random/stratified/group/time/rolling/out-of-time). Seasonality Advisor, Structural Break Detection (аутэйджи, миграции, изменения трекинга, цен, политик, релизы, изменения схемы, макро-события) с фиксацией решения include/exclude/downweight/separate regime/indicator. Data Sufficiency Advisor (без правила "нужно N строк") + learning curves + публичные бенчмарки как signal, не proof.

Labeling Layer: источники меток (human_expert, human_crowd, business_outcome, operational_system, rule_based, weak_supervision, LLM_generated, pseudo_label, external_dataset, synthetic) с хранением provenance (value, source, confidence, annotator, created_at, available_at, version, guideline_version). Сначала проверка естественных outcome-меток. Если нужна ручная разметка — annotation guidelines, label schema, edge cases, QC, adjudication, inter-annotator agreement (Kappa/Alpha). Альтернативы: weak supervision, semi-supervised, self-supervised, transfer learning, pseudo-labeling, active learning, programmatic labeling, LLM-assisted labeling, synthetic data, external data. Decision flow выбора стратегии разметки. Gold Evaluation Set — независимый, репрезентативный, качественно размеченный, версионированный, замороженный, защищённый от contamination, PIT-корректный; порог качества выше, чем у train. Active Learning Queue как часть continuous learning.

Data Readiness Gate — чеклист из 13 пунктов, статус READY/CONDITIONAL/NOT READY, критические провалы блокируют моделирование. Data Readiness Report как артефакт.

Baseline first. Model Metric Advisor: цепочка business objective → KPI → decision → DS task → target → model metric → threshold/policy → online behavior → business outcome. Business-aware offline evaluation (expected business value вместо голого ROC-AUC). Impact Chain: model metric → operational/proxy metric → action → online outcome → business KPI, каждая связь со статусом hypothesized / observationally_supported / experimentally_validated / rejected.

Analytics Agent: evidence-based investigation (question → hypotheses → data request → analysis → observation → next hypothesis → alternative explanation → validation → conclusion) + Analytical Playbook из 18 шагов. Tools: reusable (run_sql, run_python, calculate_statistics, compare_periods, compare_segments, detect_anomalies, forecast_timeseries, run_statistical_test, plot_data, retrieve_documents) и project-specific (predict_churn, forecast_sku_demand, calculate_ltv, marketing_attribution, inventory_simulation, clinical_risk_model). Принцип: LLM решает ЧТО считать → tool считает → LLM интерпретирует. Knowledge Base / RAG. Разделение типов знания: Session State, Project Memory, Knowledge Base, Learned Knowledge, Experiment Knowledge.

Adaptive Multi-Agent: 4 стратегии исполнения — SIMPLE (agent→tools→answer), STANDARD (+validator+reviewer), PARALLEL_ANALYSIS (orchestrator → analyst/DS-ML/knowledge → synthesis → review), HIGH_ASSURANCE (primary → deterministic validation → independent reviewer model → human approval). Execution Router учитывает complexity, uncertainty, risk, cost of error, sensitivity, historical failure rate, reviewer benefit, latency, cost. Multi-model orchestration (analyst — модель A, reviewer — модель B) только если evals подтверждают выигрыш. Reviewer/Critic пытается опровергнуть вывод (unsupported claims, semantic mistakes, alternative hypotheses, causal overclaiming, missing segments, temporal bias, ignored evidence). Deterministic Validator (SQL, схема, формулы, численная согласованность, размеры выборок, неполные периоды, статистические допущения, правила лика, бизнес-правила, права на инструменты).

Experimentation & Causal Layer: Experiment Advisor (hypothesis, control, treatment, randomization unit, primary metric, business KPI, secondary, guardrails, MDE, power, sample size, duration, eligibility, stopping rules); AI объясняет, детерминированный движок считает. Типы: A/B, RCT, holdout, champion/challenger, switchback, geo, cluster randomization, phased rollout, stepped-wedge, quasi-experimental, симуляция/бэктест. Lifecycle: offline eval → shadow → canary → controlled experiment → causal effect → business KPI → ship/iterate/reject. Результаты экспериментов становятся знанием (пример: рекомендательная модель +11% NDCG offline, +4.2% CTR online, но -2.3% маржа на пользователя → REJECT).

Evals ≠ A/B: evals проверяют корректность системы (выбор метрик, определения, формулировка DS-задачи, target, детекция лика, data readiness, рекомендации по разметке, выбор инструментов, корректность SQL, статистики, дизайна эксперимента, grounding, галлюцинации, causal overclaiming, эффективность ревьюера, стоимость, латентность), эксперименты проверяют каузальный бизнес-эффект.

Continuous Learning: не самомодификация. Обучение через traces, human feedback, corrections, failures, успешные расследования, результаты экспериментов, бизнес-результаты, новые метки, дрифт, находки ревьюера. Любое новое правило проходит: NEW INFORMATION → LEARNING CANDIDATE → VALIDATION → VERSIONED UPDATE. Девять независимых петель обучения: agent strategy, business knowledge, metric, data, label, eval (production failure → eval candidate → regression eval), model (new labels → drift → retraining candidate → offline eval → experiment → champion/challenger → prod), experiment (какие offline/proxy метрики реально связаны с бизнесом), router (когда дорогая сложность окупается). Learning provenance (statement, source, scope, confidence, created_at, validated_by, status candidate/validated/rejected/deprecated, version). Изменения Semantic Layer и Metric Definitions требуют human approval.

Observability: полный trace от вопроса пользователя до бизнес-результата и learning candidate; логируются версии модели/промпта/semantic layer/metric definitions/датасета/фич, источник меток, инструменты, SQL, Python, retrieved docs, назначение эксперимента, результат ревьюера, латентность, токены, стоимость, фидбек, бизнес-результат.

Safety: read-only БД, запрет деструктивного SQL, песочница Python, allowlists инструментов и таблиц, лимиты ресурсов, таймауты, PII-контроль, аудит-логи, защита от prompt injection, отчёт о доказательствах и уверенности, human approval. HIGH_ASSURANCE для healthcare/credit/finance/employment. Multimodal — только extension point, не в MVP.

Предлагаемая структура репозитория: core/ (orchestrator, planner, executor, router, validator, reviewer, state, memory, tracing, evals), data/ (8 подмодулей), labeling/ (7), experimentation/ (6), learning/ (11), tools/ (7), project_setup/ (11 advisor-модулей), domains/, projects/<id>/ (15 подпапок), app/.

Продуктовые гипотезы: H1 переиспользуемое ядро для существенно разных проектов; H2 корректный проход business problem → KPI → DS problem → target → data → model metric → decision → outcome; H3 выявление проблем данных до моделирования; H4 удешевление разметки без потери надёжности оценки; H5 роутер выбирает сложность только когда она окупается; H6 система отличает offline improvement от каузального бизнес-эффекта и проектирует проверку; H7 контролируемое continuous learning; H8 замкнутый end-to-end цикл обучения.

# ЧТО НУЖНО ОТ ТЕБЯ

1. Главные архитектурные и методологические ошибки концепции. Что здесь принципиально не сработает и почему.
2. Где скрыты ложные предпосылки (особенно в H1 — reusable core, и в H7 — continuous learning).
3. Где переусложнение: какие из ~60 перечисленных компонентов не нужны вовсе, какие схлопываются в один.
4. Что должно быть детерминированным кодом, а что реально требует LLM. Где LLM вставлен без нужды.
5. Экономика и организационные предпосылки: что должно быть верно в компании, чтобы эта платформа вообще имела смысл. Кто пользователь и почему он не будет ею пользоваться.
6. Конкурентная реальность: чем это отличается от dbt + метрик-слоя + MLflow/W&B + feature store + Statsig/GrowthBook + существующих AI-аналитиков. Где действительно новая ценность, а где переизобретение.
7. Твой вариант радикально более простого MVP, который проверяет те же гипотезы меньшим числом компонентов. Назови, какие гипотезы MVP проверяет, а какие честно откладывает.
8. Топ-5 рисков, которые убьют проект, и ранние сигналы каждого.

Будь конкретен и жёсток. Если что-то в концепции правильно — скажи коротко, основной объём отдай критике.
